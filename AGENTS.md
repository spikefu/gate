## Rules this repo is held to

Generated by `gate rules` from `gate.toml`. Do not edit this section; change `gate.toml` and rerun.

Run `gate check --changed` before you finish. It must pass.

### Limits

- Functions: cyclomatic complexity at most 15 (warns above 10), at most 80 lines, at most 5 parameters.
- Files: at most 500 lines (warns above 300).
- Test files: at most 1000 lines.

### Boundaries

- Modules must not import each other in a loop. Type-only imports, and imports inside a function, do not count.
- A Python name or module starting with `_` is private to the folder it is in. Do not import it from anywhere else.
- A file importing more than 15 of this repo's modules gets a warning: unless it is where the program is wired together, split it.
- `src/gate/checks` must not import `src/gate/runner.py`.
- `src/gate/checks` must not import `src/gate/cli.py`.
- `src/gate/lang` must not import `src/gate/checks`.

### Suppressions

- Do not switch a check off to get past it. Adding any of these fails the gate: lint ignores (`# noqa`, `eslint-disable`, and the like); type-checker ignores (`# type: ignore`, `@ts-ignore`, `as any`); skipped or expected-to-fail tests; coverage exclusions.
- Fix the cause. If a suppression is truly the right answer, say why in your report and leave it failing: accepting it is the human's decision.

### Duplication

- Do not copy code. A block of 10 or more lines identical to code elsewhere in the repo fails (test files are exempt).
- Before writing a helper, search for one that already does it. If two places need the same code, move it somewhere both can use.

### Dead code

- Do not leave code nothing uses. A function, class, constant or type whose name appears nowhere else in the repo fails.
- Export only what another file uses. An `export` on something only its own file uses fails.
- When you change approach, delete what the first attempt left behind. Do not keep it "in case".

### Change size

- Keep each change small enough to review. Past 400 added lines of non-test code in one uncommitted change, gate warns.
- When it does, stop at the next natural point and say so in your report. Do not carry on, and do not commit on your own to reset the count.

### Shared state

- Do not add module-level variables that code reassigns: a top-level `let` or `var`, or a Python `global`. Adding one fails.
- Pass the value in, return it, or keep it in an object with a clear owner.

### Checks

- `gate check --profile fast` (default): syntax, complexity, size, boundaries, suppressions, test-integrity, duplication, dead-code, change-size, mutable-state, lint.
- `gate check --profile full`: syntax, complexity, size, boundaries, suppressions, test-integrity, duplication, dead-code, change-size, mutable-state, lint, typecheck, unit, integration.
- `lint` runs `ruff check .`.
- `typecheck` runs `mypy`.
- `unit` runs `pytest -q tests/unit`.
- `integration` runs `pytest -q tests/integration`.

### Existing violations

- Violations that predate these rules are recorded in `.gate/baseline.json`. Do not make them worse.
- Never run `gate baseline --accept`, edit the baseline by hand, or change a limit to make a finding go away.
- Never delete, skip, or loosen a test to get a check to pass. A change that leaves fewer tests or assertions than it started with fails; if one should go, say why in your report.

### Improving these rules

These rules are a draft, and you are expected to challenge them. Passing the gate is the minimum; noticing where it falls short is part of the work. As you go, look for:

- a problem that got through because no rule or check covers it
- a limit that is looser than the code needs, or stricter than is useful
- a boundary the code keeps to that is not written down
- a finding that is wrong: say so instead of working around it
- a check that was skipped, or that no profile runs

Run `gate gaps` for the weaknesses gate can see for itself, then add what only a reader of the code can see.

Passing the gate does not make a design good. `gate metrics` lists facts about each file and folder: what depends on what, what is reached into, where state is shared. Use them to check your own change for units with more than one job, internals used from outside, and effects a caller would not expect.

Say what you found in your report, even when nobody asked, with the evidence and the exact change you propose: the `gate.toml` edit, or a script to add as a `[[command]]` check when gate has no check for it. Propose; do not apply. What the rules are is the human's decision.
